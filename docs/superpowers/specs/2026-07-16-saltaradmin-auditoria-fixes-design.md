# SaltarAdmin — Correcciones restantes de la auditoría (Design)

> Tercera ronda de trabajo tras la auditoría de 11 expertos. Los 6 bloqueantes críticos ya se corrigieron (RLS+Clerk, doble reserva, solapamiento de bloqueos, aviso de privacidad+borrado, separación dev/prod) o se rechazaron explícitamente (licencia comercial de FullCalendar Scheduler). Esta ronda cubre el resto de hallazgos "Alto"/"Medio" de los 11 informes, agrupados en tres bloques confirmados por el usuario: bugs de código y accesibilidad, rendimiento rápido, e infraestructura/herramientas (ESLint + tests). Sentry queda explícitamente fuera (requiere una cuenta externa que el usuario no quiere crear todavía).

## Fuera de alcance (confirmado explícitamente)

- **Licencia comercial de FullCalendar Scheduler** — ya rechazada por el usuario en una ronda anterior.
- **Sentry / monitorización de errores** — requiere cuenta externa; el usuario decidió omitirlo esta ronda.
- **Features de producto/negocio** (precio y estado de pago, multi-unidad por artículo, hora/dirección de entrega, panel "Hoy", auto-completado de estado, exportar CSV) — son decisiones de negocio, no bugs; no se tocan sin que el usuario las pida explícitamente.
- **Extraer un `<Modal>` compartido de verdad** (colapsar la duplicación de estructura entre los 6 modales) — la introducción de `react-modal` (bloque 1 de abajo) ya resuelve el problema de accesibilidad que motivaba esta sugerencia; la deduplicación completa de JSX es una refactorización más grande, aparcada.
- **Migraciones versionadas con Supabase CLI** — cambio de proceso/herramienta, no de código.

## Bloque 1 — Bugs de código y accesibilidad

1. **Cabeceras de seguridad** (`vercel.json`, nuevo): CSP básica (permitiendo Clerk, Supabase, Google Fonts), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`.
2. **`.env.example` corregido**: sustituir `VITE_API_URL` (no usado en ningún sitio) por las 3 variables reales: `VITE_CLERK_PUBLISHABLE_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, con comentarios de dónde obtener cada una.
3. **`README.md`** (nuevo, raíz del proyecto): qué es SaltarAdmin, instalación (`npm install`, variables de entorno, `npm run dev`), y un índice enlazando `docs/superpowers/specs/` y `docs/superpowers/plans/` — el hallazgo de Mantenibilidad de mayor impacto según la propia auditoría.
4. **`ErrorBoundary`** (`src/components/ErrorBoundary.tsx`, nuevo): componente de clase estándar de React, captura errores de render y muestra un mensaje de recuperación en español ("Algo ha ido mal. Recarga la página.") en vez de pantalla en blanco. Se monta en `src/main.tsx` envolviendo `<App />` (dentro de `ClerkProvider`, para que el árbol de Clerk siga montado y `UserButton`/`SignInButton` sigan funcionando si el error es solo de una vista interior).
5. **`getErrorMessage(err)`** (`src/lib/errors.ts`, nuevo): helper único que centraliza la extracción de un mensaje legible de un error — hoy el patrón `err instanceof Error ? err.message : 'mensaje genérico'` nunca es cierto para errores de Supabase (son objetos planos `{ message, code, ... }`, no instancias de `Error`), así que el usuario nunca ve la causa real. El helper comprueba, en orden: `err instanceof Error` → `err.message`; si no, objeto con propiedad `message` de tipo string (forma de `PostgrestError`) → esa `message`; si no, el `fallback` pasado como segundo argumento. Se aplica en los ~12 sitios que hoy repiten el patrón manual, sustituyendo cada `catch` para usar `getErrorMessage(err, 'mensaje de fallback existente')` — el mensaje de fallback de cada sitio se mantiene igual que hoy, solo cambia la extracción del mensaje real cuando existe.
6. **Validación de la clave de Clerk al arrancar** (`src/main.tsx`): si `VITE_CLERK_PUBLISHABLE_KEY` falta o está vacía, no renderizar `ClerkProvider` (que fallaría con pantalla en blanco) — mostrar un mensaje de configuración claro en español en su lugar.
7. **Foco de teclado en los 6 modales** — usar la dependencia `react-modal` (`^3.16.3`, ya instalada con sus tipos, actualmente sin usar — "dependencia fantasma" según la auditoría) en `ReserveModal.tsx`, `PrivacyNoticeModal.tsx`, `ManageArticleModal.tsx`, `GestionarReservasModal.tsx`, `ArticleDetailModal.tsx`, `DayReservationsModal.tsx`. Cada modal cambia su `<div className="fixed inset-0 bg-black bg-opacity-50 ...">` exterior por `<Modal isOpen={isOpen} onRequestClose={...} ariaHideApp={false} className="..." overlayClassName="...">` de `react-modal`, conservando exactamente las mismas clases de Tailwind ya aplicadas en la ronda de rediseño (los mismos estilos de tarjeta/overlay, sin cambios visuales). `react-modal` gestiona automáticamente: `role="dialog"`, mover el foco al abrir, atraparlo dentro (Tab no se escapa), devolverlo al elemento que abrió el modal al cerrar, y cerrar con Escape. `ariaHideApp={false}` porque el proyecto no usa el patrón `appElement` de `react-modal` (evita el warning de consola sin necesitar tocar `main.tsx` para registrar el elemento raíz de la app).
8. **Etiquetas accesibles en buscadores/selects** que hoy solo tienen `placeholder`: el input de búsqueda de `GestionarReservasModal.tsx` y el de `ReservationHistory.tsx`, y el `<select>` de estado de `ReservationHistory.tsx` — añadir `aria-label` descriptivo a cada uno (p. ej. `aria-label="Buscar por nombre o teléfono"`, `aria-label="Cambiar estado de la reserva"`), sin cambiar el `placeholder` visible existente.
9. **Nombre de artículo accesible por teclado en el calendario** (`Calendar.tsx`): hoy `resourceLabelDidMount` añade un listener de clic crudo sobre el DOM del label de FullCalendar, sin `tabIndex` ni rol. Se añade `info.el.setAttribute('role', 'button')`, `info.el.setAttribute('tabindex', '0')`, y un listener de `keydown` que activa el mismo `onArticuloClickRef.current(...)` cuando la tecla es Enter o Espacio — mismo patrón de activación que un `<button>` real, sin envolver el DOM de FullCalendar en un componente React (no es controlable directamente).

## Bloque 2 — Rendimiento rápido

10. **`React.lazy` para las dos vistas de calendario** (`src/App.tsx`): `Calendar` y `MonthCalendarView` pasan de import estático a `React.lazy(() => import('./components/Calendar'))` / `React.lazy(() => import('./components/MonthCalendarView'))`, envueltos en un único `<Suspense fallback={...}>` alrededor del `<main>` existente (fallback: mismo texto "Cargando..." ya usado en otros sitios del proyecto, sin librería nueva). Saca el plugin más pesado de FullCalendar (Scheduler/resource-timeline) del bundle inicial para quien entra directamente al Historial o a Gestionar Artículos.
11. **Redimensionar imágenes en el cliente antes de subir** (`src/lib/images.ts`, nuevo + uso en `ManageArticleModal.tsx`): función `resizeImage(file: File, maxDimension: number): Promise<File>` que carga el archivo en un `<canvas>`, escala manteniendo proporción si el lado mayor supera `maxDimension` (1200px), y re-exporta como `File` (mismo tipo MIME, calidad JPEG/WebP 0.85 si aplica). Se llama justo antes de `uploadArticuloImagen` en `handleSubmit`, después de las validaciones de tamaño/tipo ya existentes — el límite de 5MB sigue validando el archivo original tal cual lo eligió el usuario, el redimensionado ocurre después, no lo sustituye.

## Bloque 3 — Infraestructura/herramientas

12. **ESLint** (`eslint.config.js`, nuevo — formato flat config, compatible con ESLint 9 que ya viene con Vite 5/React 18 del proyecto): `typescript-eslint` (recomendado), `eslint-plugin-react-hooks` (reglas de hooks), `eslint-plugin-jsx-a11y` (recomendado — refuerza el bloque de accesibilidad de arriba y previene regresiones futuras). Script nuevo en `package.json`: `"lint": "eslint ."`. Se ejecuta una vez sobre todo `src/` y se corrigen los errores reales que aparezcan (no solo advertencias de estilo) — si aparecen más de ~15 hallazgos no triviales, se prioriza y se documentan los restantes en vez de bloquear esta ronda por completo.
13. **Vitest** (`vitest.config.ts`, nuevo, reutilizando la config de Vite existente vía `vite.config.ts`): se extrae `intervalosSolapan(aInicio: string, aFin: string, bInicio: string, bFin: string): boolean` como función pura en `src/lib/disponibilidad.ts` (misma semántica de intervalo semiabierto `[inicio, fin)` que ya usa `hayConflictoDisponibilidad` vía `.lt()/.gt()` en la query — esta función pura documenta y testea esa semántica de forma aislada, tal como pidió el experto de QA; `hayConflictoDisponibilidad` en `supabase.ts` no cambia su lógica de query, solo se le añade un comentario que remite a `disponibilidad.ts` como la especificación de referencia). 8 casos de test cubriendo: solapamiento total, solapamiento parcial (por la izquierda y por la derecha), un intervalo contiene al otro, intervalos adyacentes sin solape (`aFin === bInicio`), intervalos idénticos, sin relación (muy separados), y el caso de turno de un mismo día. Script nuevo en `package.json`: `"test": "vitest run"`.
14. **`docs/supabase-schema.sql`** (nuevo, documentación best-effort): reconstrucción del `CREATE TABLE` de las 3 tablas (`articulos`, `reservas`, `bloqueos`) tal como existen hoy en producción, con la FK de `reservas.articulo_id`/`bloqueos.articulo_id` → `articulos.id` declarada explícitamente `ON DELETE RESTRICT` (el comportamiento que el código ya asume al capturar el código de error `23503` en `ManageArticleModal.tsx` — este script documenta esa asunción por escrito por primera vez, ya que no existía ningún script de creación de esquema versionado en el repo). Este archivo es solo documentación/referencia — no se ejecuta contra la base de datos real como parte de esta ronda, ya que reemplazar una tabla existente no es una operación segura de aplicar a ciegas; queda como referencia para que el usuario confirme manualmente si su esquema real coincide.

## Verificación

- Con el bypass temporal de sesión: recorrer los 6 modales confirmando que abren/cierran igual que antes visualmente, que Tab queda atrapado dentro de cada uno, que Escape cierra, y que el foco vuelve al botón que abrió el modal.
- Provocar un error de Supabase real (p. ej. crear una reserva solapada) y confirmar que el mensaje mostrado es el mensaje específico ya existente en el código (no el genérico "Something went wrong" ni un error crudo de Supabase sin traducir) — `getErrorMessage` no debe cambiar ningún texto de error ya escrito a mano en el código, solo arreglar los casos donde hoy se pierde.
- `npm run build` sin errores; `npm run lint` sin errores (advertencias documentadas si las hay); `npm run test` en verde.
- Confirmar visualmente que `React.lazy` no rompe ninguna transición entre pestañas (breve "Cargando..." aceptable la primera vez que se visita cada vista).
- Subir una imagen de varios MB a un artículo y confirmar que la subida a Supabase Storage resulta en un archivo más pequeño que el original.

## Fuera de alcance (repetido para claridad)

Sentry, ESLint/tests de cobertura exhaustiva (esto es un arranque razonable, no una suite completa), features de producto, licencia de FullCalendar, extracción completa de `<Modal>` compartido, migraciones versionadas con Supabase CLI, aplicar `docs/supabase-schema.sql` contra la base de datos real.
